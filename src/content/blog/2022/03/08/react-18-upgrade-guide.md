<Intro>

Как мы поделились в [посте о релизе](/blog/2022/03/29/react-v18), React 18 представляет новые возможности, основанные на нашем новом конкурентном рендерере, с постепенной стратегией внедрения для существующих приложений. В этом посте мы проведем вас через шаги по обновлению до React 18.

Пожалуйста, [сообщайте о любых проблемах](https://github.com/facebook/react/issues/new/choose), с которыми вы столкнетесь при обновлении до React 18.

</Intro>

<Note>

Пользователи React Native, React 18 будет доступен в будущей версии React Native. Это связано с тем, что React 18 полагается на новую архитектуру React Native для использования новых возможностей, представленных в этом посте. Для получения дополнительной информации см. [ключевую речь React Conf здесь](https://www.youtube.com/watch?v=FZ0cG47msEk&t=1530s).

</Note>

## Установка {/*installing*/}

Чтобы установить последнюю версию React:

```bash
npm install react react-dom
```

Или если вы используете yarn:

```bash
yarn add react react-dom
```

## Обновления API клиентского рендеринга {/*updates-to-client-rendering-apis*/}

Когда вы впервые установите React 18, вы увидите предупреждение в консоли:

<ConsoleBlock level="error">

ReactDOM.render больше не поддерживается в React 18. Используйте createRoot вместо этого. Пока вы не переключитесь на новый API, ваше приложение будет вести себя так, как будто оно работает на React 17. Подробнее: https://reactjs.org/link/switch-to-createroot

</ConsoleBlock>

React 18 представляет новый API корневого узла, который обеспечивает лучшую эргономику для управления корневыми узлами. Новый API корневого узла также включает новый конкурентный рендерер, который позволяет вам использовать конкурентные возможности.

```js
// До
import { render } from 'react-dom';
const container = document.getElementById('app');
render(<App tab="home" />, container);

// После
import { createRoot } from 'react-dom/client';
const container = document.getElementById('app');
const root = createRoot(container); // createRoot(container!) если вы используете TypeScript
root.render(<App tab="home" />);
```

Мы также изменили `unmountComponentAtNode` на `root.unmount`:

```js
// До
unmountComponentAtNode(container);

// После
root.unmount();
```

Мы также удалили колбэк из render, так как он обычно не дает ожидаемого результата при использовании Suspense:

```js
// До
const container = document.getElementById('app');
render(<App tab="home" />, container, () => {
  console.log('rendered');
});

// После
function AppWithCallbackAfterRender() {
  useEffect(() => {
    console.log('rendered');
  });

  return <App tab="home" />
}

const container = document.getElementById('app');
const root = createRoot(container);
root.render(<AppWithCallbackAfterRender />);
```

<Note>

Прямой замены для старого API колбэка render не существует — это зависит от вашего конкретного случая использования. См. пост рабочей группы [Replacing render with createRoot](https://github.com/reactwg/react-18/discussions/5) для получения дополнительной информации.

</Note>

Наконец, если ваше приложение использует серверный рендеринг с гидратацией, обновите `hydrate` до `hydrateRoot`:

```js
// До
import { hydrate } from 'react-dom';
const container = document.getElementById('app');
hydrate(<App tab="home" />, container);

// После
import { hydrateRoot } from 'react-dom/client';
const container = document.getElementById('app');
const root = hydrateRoot(container, <App tab="home" />);
// В отличие от createRoot, здесь не требуется отдельный вызов root.render().
```

Для получения дополнительной информации см. обсуждение рабочей группы [здесь](https://github.com/reactwg/react-18/discussions/5).

<Note>

**Если ваше приложение не работает после обновления, проверьте, обернуто ли оно в `<StrictMode>`.** [Strict Mode стал строже в React 18](#updates-to-strict-mode), и не все ваши компоненты могут быть устойчивы к новым проверкам, которые он добавляет в режиме разработки. Если удаление Strict Mode устраняет проблему с вашим приложением, вы можете удалить его во время обновления, а затем добавить обратно (либо в начале, либо для части дерева), исправив проблемы, на которые он указывает.

</Note>

## Обновления API серверного рендеринга {/*updates-to-server-rendering-apis*/}

В этом релизе мы перерабатываем наши API `react-dom/server` для полной поддержки Suspense на сервере и потоковой передачи SSR. В рамках этих изменений мы устареваем старый API потоковой передачи Node, который не поддерживает инкрементальную потоковую передачу Suspense на сервере.

Использование этого API теперь будет выдавать предупреждение:

* `renderToNodeStream`: **Устарело ⛔️️**

Вместо этого для потоковой передачи в средах Node используйте:
* `renderToPipeableStream`: **Новый ✨**

Мы также представляем новый API для поддержки потоковой передачи SSR с Suspense для современных сред выполнения на границе сети (edge runtime), таких как Deno и Cloudflare workers:
* `renderToReadableStream`: **Новый ✨**

Следующие API продолжат работать, но с ограниченной поддержкой Suspense:
* `renderToString`: **Ограниченно** ⚠️
* `renderToStaticMarkup`: **Ограниченно** ⚠️

Наконец, этот API будет продолжать работать для рендеринга электронной почты:
* `renderToStaticNodeStream`

Для получения дополнительной информации об изменениях в API серверного рендеринга см. пост рабочей группы [Upgrading to React 18 on the server](https://github.com/reactwg/react-18/discussions/22), [подробный разбор новой архитектуры SSR с Suspense](https://github.com/reactwg/react-18/discussions/37) и выступление [Shaundai Person](https://twitter.com/shaundai) о [Streaming Server Rendering with Suspense](https://www.youtube.com/watch?v=pj5N-Khihgc) на React Conf 2021.

## Обновления определений TypeScript {/*updates-to-typescript-definitions*/}

Если ваш проект использует TypeScript, вам потребуется обновить зависимости `@types/react` и `@types/react-dom` до последних версий. Новые типы более безопасны и обнаруживают проблемы, которые раньше игнорировались проверкой типов. Наиболее заметное изменение заключается в том, что проп `children` теперь должен быть явно указан при определении пропсов, например:

```typescript{3}
interface MyButtonProps {
  color: string;
  children?: React.ReactNode;
}
```

См. [запрос на слияние для типизаций React 18](https://github.com/DefinitelyTyped/DefinitelyTyped/pull/56210) для полного списка изменений, касающихся только типов. Он ссылается на примеры исправлений в типах библиотек, чтобы вы могли увидеть, как адаптировать свой код. Вы можете использовать [автоматизированный скрипт миграции](https://github.com/eps1lon/types-react-codemod), чтобы быстрее перенести код вашего приложения на новые и более безопасные типизации.

Если вы обнаружите ошибку в типизациях, пожалуйста, [создайте issue](https://github.com/DefinitelyTyped/DefinitelyTyped/discussions/new?category=issues-with-a-types-package) в репозитории DefinitelyTyped.

## Автоматическая пакетная обработка {/*automatic-batching*/}

React 18 добавляет улучшения производительности "из коробки", выполняя больше пакетной обработки по умолчанию. Пакетная обработка — это когда React группирует несколько обновлений состояния в один повторный рендеринг для повышения производительности. До React 18 мы группировали обновления только внутри обработчиков событий React. Обновления внутри промисов, setTimeout, нативных обработчиков событий или любых других событий по умолчанию не группировались в React:

```js
// До React 18 группировались только события React

function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерисуется только один раз в конце (это пакетная обработка!)
}

setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерисуется дважды, один раз для каждого обновления состояния (без пакетной обработки)
}, 1000);
```


Начиная с React 18 с `createRoot`, все обновления будут автоматически группироваться, независимо от их источника. Это означает, что обновления внутри тайм-аутов, промисов, нативных обработчиков событий или любых других событий будут группироваться так же, как и обновления внутри событий React:

```js
// После React 18 обновления внутри тайм-аутов, промисов,
// нативных обработчиков событий или любых других событий группируются.

function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерисуется только один раз в конце (это пакетная обработка!)
}

setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React перерисуется только один раз в конце (это пакетная обработка!)
}, 1000);
```

Это обратно несовместимое изменение, но мы ожидаем, что оно приведет к уменьшению работы по рендерингу и, следовательно, к повышению производительности ваших приложений. Чтобы отказаться от автоматической пакетной обработки, вы можете использовать `flushSync`:

```js
import { flushSync } from 'react-dom';

function handleClick() {
  flushSync(() => {
    setCounter(c => c + 1);
  });
  // К этому моменту React обновил DOM
  flushSync(() => {
    setFlag(f => !f);
  });
  // К этому моменту React обновил DOM
}
```

Для получения дополнительной информации см. [подробный разбор Automatic batching](https://github.com/reactwg/react-18/discussions/21).

## Новые API для библиотек {/*new-apis-for-libraries*/}

В рабочей группе React 18 мы сотрудничали с мейнтенерами библиотек для создания новых API, необходимых для поддержки конкурентного рендеринга для конкретных случаев использования в таких областях, как стили и внешние хранилища. Для поддержки React 18 некоторым библиотекам может потребоваться перейти на один из следующих API:

* `useSyncExternalStore` — это новый хук, который позволяет внешним хранилищам поддерживать конкурентное чтение, принудительно синхронизируя обновления хранилища. Этот новый API рекомендуется для любых библиотек, которые интегрируются с состоянием, внешним по отношению к React. Для получения дополнительной информации см. [обзорный пост useSyncExternalStore](https://github.com/reactwg/react-18/discussions/70) и [детали API useSyncExternalStore](https://github.com/reactwg/react-18/discussions/86).
* `useInsertionEffect` — это новый хук, который позволяет библиотекам CSS-in-JS решать проблемы производительности при внедрении стилей во время рендеринга. Если вы еще не создали библиотеку CSS-in-JS, мы не ожидаем, что вы когда-либо будете использовать этот хук. Этот хук будет выполняться после мутации DOM, но до того, как эффекты макета прочитают новый макет. Это решает проблему, которая уже существует в React 17 и ниже, но становится еще более важной в React 18, поскольку React уступает управление браузеру во время конкурентного рендеринга, давая ему возможность пересчитать макет. Для получения дополнительной информации см. [Руководство по обновлению библиотек для `<style>`](https://github.com/reactwg/react-18/discussions/110).

React 18 также представляет новые API для конкурентного рендеринга, такие как `startTransition`, `useDeferredValue` и `useId`, о которых мы подробнее рассказываем в [посте о релизе](/blog/2022/03/29/react-v18).

## Обновления Strict Mode {/*updates-to-strict-mode*/}

В будущем мы хотим добавить возможность React добавлять и удалять части UI с сохранением состояния. Например, когда пользователь переключается с экрана и обратно, React должен иметь возможность немедленно отобразить предыдущий экран. Для этого React будет размонтировать и повторно монтировать деревья, используя то же состояние компонента, что и раньше.

Эта функция даст React лучшую производительность из коробки, но требует, чтобы компоненты были устойчивы к тому, что эффекты монтируются и уничтожаются несколько раз. Большинство эффектов будут работать без изменений, но некоторые эффекты предполагают, что они монтируются или уничтожаются только один раз.

Чтобы помочь выявить эти проблемы, React 18 вводит новую проверку только для режима разработки в Strict Mode. Эта новая проверка будет автоматически размонтировать и повторно монтировать каждый компонент при первом монтировании компонента, восстанавливая предыдущее состояние при втором монтировании.

До этого изменения React монтировал компонент и создавал эффекты:

```
* React монтирует компонент.
    * Создаются эффекты макета (Layout effects).
    * Создаются эффекты (Effect effects).
```

В Strict Mode в React 18 React будет симулировать размонтирование и повторное монтирование компонента в режиме разработки:

```
* React монтирует компонент.
    * Создаются эффекты макета (Layout effects).
    * Создаются эффекты (Effect effects).
* React симулирует размонтирование компонента.
    * Эффекты макета уничтожаются.
    * Эффекты уничтожаются.
* React симулирует монтирование компонента с предыдущим состоянием.
    * Запускается код настройки эффекта макета.
    * Запускается код настройки эффекта.
```

Для получения дополнительной информации см. сообщения Рабочей группы [Adding Reusable State to StrictMode](https://github.com/reactwg/react-18/discussions/19) и [How to support Reusable State in Effects](https://github.com/reactwg/react-18/discussions/18).

## Настройка тестовой среды {/*configuring-your-testing-environment*/}

Когда вы впервые обновите свои тесты для использования `createRoot`, вы можете увидеть это предупреждение в консоли тестов:

<ConsoleBlock level="error">

Текущая тестовая среда не настроена для поддержки act(...)

</ConsoleBlock>

Чтобы исправить это, установите `globalThis.IS_REACT_ACT_ENVIRONMENT` в `true` перед запуском теста:

```js
// В вашем файле настройки тестов
globalThis.IS_REACT_ACT_ENVIRONMENT = true;
```

Цель этого флага — сообщить React, что он работает в среде, подобной модульному тестированию. React будет выводить полезные предупреждения, если вы забудете обернуть обновление в `act`.

Вы также можете установить флаг в `false`, чтобы сообщить React, что `act` не требуется. Это может быть полезно для сквозных тестов, которые имитируют полную браузерную среду.

В конечном итоге мы ожидаем, что библиотеки тестирования будут настраивать это автоматически. Например, [следующая версия React Testing Library имеет встроенную поддержку React 18](https://github.com/testing-library/react-testing-library/issues/509#issuecomment-917989936) без какой-либо дополнительной настройки.

[Более подробная информация об API тестирования `act` и связанных изменениях](https://github.com/reactwg/react-18/discussions/102) доступна в рабочей группе.

## Прекращение поддержки Internet Explorer {/*dropping-support-for-internet-explorer*/}

В этом выпуске React прекращает поддержку Internet Explorer, поддержка которого [заканчивается 15 июня 2022 года](https://blogs.windows.com/windowsexperience/2021/05/19/the-future-of-internet-explorer-on-windows-10-is-in-microsoft-edge). Мы вносим это изменение сейчас, потому что новые функции, представленные в React 18, построены с использованием современных браузерных функций, таких как микрозадачи, которые не могут быть адекватно полифиллены в IE.

Если вам нужно поддерживать Internet Explorer, мы рекомендуем остаться на React 17.

## Другие критические изменения {/*other-breaking-changes*/}

* **Согласованное время выполнения `useEffect`**: React теперь всегда синхронно выполняет функции эффектов, если обновление было вызвано дискретным событием пользовательского ввода, таким как событие клика или нажатия клавиши. Ранее поведение не всегда было предсказуемым или согласованным.
* **Более строгие ошибки гидратации**: Несоответствия гидратации из-за отсутствия или лишнего текстового содержимого теперь обрабатываются как ошибки, а не предупреждения. React больше не будет пытаться "исправлять" отдельные узлы, вставляя или удаляя узел на клиенте, чтобы соответствовать разметке сервера, и будет возвращаться к рендерингу на клиенте до ближайшей границы `<Suspense>` в дереве. Это гарантирует согласованность дерева гидратации и устраняет потенциальные проблемы с конфиденциальностью и безопасностью, которые могут возникнуть из-за несоответствий гидратации.
* **Деревья `Suspense` всегда согласованы**: Если компонент приостанавливается до того, как он будет полностью добавлен в дерево, React не добавит его в дерево в неполном состоянии и не вызовет его эффекты. Вместо этого React полностью отбросит новое дерево, дождется завершения асинхронной операции, а затем снова попытается выполнить рендеринг с нуля. React будет выполнять попытку рендеринга параллельно и без блокировки браузера.
* **Эффекты макета с `Suspense`**: Когда дерево повторно приостанавливается и возвращается к резервному варианту, React теперь будет очищать эффекты макета, а затем воссоздавать их, когда содержимое внутри границы снова отобразится. Это исправляет проблему, которая мешала библиотекам компонентов правильно измерять макет при использовании с `Suspense`.
* **Новые требования к среде JavaScript**: React теперь зависит от современных браузерных функций, включая `Promise`, `Symbol` и `Object.assign`. Если вы поддерживаете старые браузеры и устройства, такие как Internet Explorer, которые не предоставляют современные браузерные функции нативно или имеют несовместимые реализации, рассмотрите возможность включения глобального полифилла в ваше скомпилированное приложение.

## Другие заметные изменения {/*other-notable-changes*/}

### React {/*react*/}

* **Компоненты теперь могут возвращать `undefined`**: React больше не выдает предупреждение, если вы возвращаете `undefined` из компонента. Это делает допустимые значения возврата компонента согласованными со значениями, допустимыми в середине дерева компонентов. Мы рекомендуем использовать линтер, чтобы предотвратить ошибки, такие как забытый оператор `return` перед JSX.
* **В тестах предупреждения `act` теперь являются необязательными**: Если вы запускаете сквозные тесты, предупреждения `act` не нужны. Мы ввели [механизм выбора](https://github.com/reactwg/react-18/discussions/102), чтобы вы могли включать их только для модульных тестов, где они полезны и необходимы.
* **Нет предупреждений о `setState` на размонтированных компонентах**: Ранее React предупреждал об утечках памяти, когда вы вызывали `setState` на размонтированном компоненте. Это предупреждение было добавлено для подписок, но люди в основном сталкивались с ним в сценариях, где установка состояния допустима, а обходные пути ухудшают код. Мы [удалили](https://github.com/facebook/react/pull/22114) это предупреждение.
* **Нет подавления логов консоли**: Когда вы используете Strict Mode, React дважды рендерит каждый компонент, чтобы помочь вам найти неожиданные побочные эффекты. В React 17 мы подавляли логи консоли для одного из двух рендеров, чтобы сделать логи более читаемыми. В ответ на [отзывы сообщества](https://github.com/facebook/react/issues/21783) о том, что это сбивает с толку, мы убрали подавление. Вместо этого, если у вас установлены React DevTools, рендеры второго лога будут отображаться серым цветом, и будет опция (по умолчанию отключена) для их полного подавления.
* **Улучшенное использование памяти**: React теперь очищает больше внутренних полей при размонтировании, что снижает влияние незафиксированных утечек памяти, которые могут существовать в коде вашего приложения.

### React DOM Server {/*react-dom-server*/}

* **`renderToString`**: Больше не будет выдавать ошибку при приостановке на сервере. Вместо этого он будет выводить HTML-заполнитель для ближайшего `<Suspense>`-элемента, а затем повторно попытается отрендерить тот же контент на клиенте. Тем не менее, рекомендуется перейти на потоковый API, такой как `renderToPipeableStream` или `renderToReadableStream`.
* **`renderToStaticMarkup`**: Больше не будет выдавать ошибку при приостановке на сервере. Вместо этого он будет выводить HTML-заполнитель для ближайшего `<Suspense>`-элемента.
