## React Server Components {/*react-server-components*/}

React Server Components (или RSC) — это новая архитектура приложений, разработанная командой React.

Мы впервые поделились нашими исследованиями по RSC в [вводной презентации](/blog/2020/12/21/data-fetching-with-react-server-components) и [RFC](https://github.com/reactjs/rfcs/pull/188). Чтобы напомнить, мы представляем новый вид компонента — Server Components — которые запускаются заранее и исключаются из вашего пакета JavaScript. Server Components могут запускаться во время сборки, позволяя вам читать из файловой системы или получать статический контент. Они также могут запускаться на сервере, позволяя вам получать доступ к вашему слою данных без необходимости создавать API. Вы можете передавать данные через пропсы от Server Components к интерактивным Client Components в браузере.

RSC сочетает в себе простую модель мышления «запрос/ответ» серверно-ориентированных многостраничных приложений с бесшовной интерактивностью клиентно-ориентированных одностраничных приложений, предоставляя вам лучшее из обоих миров.

С момента нашего последнего обновления мы объединили [React Server Components RFC](https://github.com/reactjs/rfcs/blob/main/text/0188-server-components.md) для ратификации предложения. Мы решили нерешенные вопросы с предложением [React Server Module Conventions](https://github.com/reactjs/rfcs/blob/main/text/0227-server-module-conventions.md) и достигли консенсуса с нашими партнерами, чтобы использовать соглашение `"use client"`. Эти документы также служат спецификацией для того, что должна поддерживать RSC-совместимая реализация.

Самое большое изменение заключается в том, что мы представили [`async` / `await`](https://github.com/reactjs/rfcs/pull/229) в качестве основного способа получения данных из Server Components. Мы также планируем поддерживать загрузку данных с клиента, представив новый Hook под названием `use`, который распаковывает Promises. Хотя мы не можем поддерживать `async / await` в произвольных компонентах в приложениях, работающих только на клиенте, мы планируем добавить поддержку для этого, когда вы структурируете свое приложение, работающее только на клиенте, аналогично тому, как структурированы приложения RSC.

Теперь, когда мы довольно хорошо разобрались с получением данных, мы изучаем другое направление: отправку данных с клиента на сервер, чтобы вы могли выполнять мутации базы данных и реализовывать формы. Мы делаем это, позволяя вам передавать функции Server Action через границу сервер/клиент, которые клиент затем может вызывать, обеспечивая бесшовный RPC. Server Actions также предоставляют вам постепенно улучшенные формы до загрузки JavaScript.

React Server Components был выпущен в [Next.js App Router](/learn/start-a-new-react-project#nextjs-app-router). Это демонстрирует глубокую интеграцию маршрутизатора, который действительно использует RSC в качестве примитива, но это не единственный способ построить RSC-совместимый маршрутизатор и фреймворк. Существует четкое разделение функций, предоставляемых спецификацией и реализацией RSC. React Server Components предназначен как спецификация для компонентов, которые работают во всех совместимых фреймворках React.

Мы обычно рекомендуем использовать существующий фреймворк, но если вам нужно создать свой собственный пользовательский фреймворк, это возможно. Создание собственного RSC-совместимого фреймворка не так просто, как нам хотелось бы, в основном из-за глубокой интеграции бандлера. Текущее поколение бандлеров отлично подходит для использования на клиенте, но они не были разработаны с первоклассной поддержкой разделения одного графа модулей между сервером и клиентом. Вот почему мы сейчас напрямую сотрудничаем с разработчиками бандлеров, чтобы встроить примитивы для RSC.

## Загрузка ресурсов {/*asset-loading*/}

[Suspense](/reference/react/Suspense) позволяет вам указать, что отображать на экране, пока данные или код для ваших компонентов еще загружаются. Это позволяет вашим пользователям постепенно видеть больше контента во время загрузки страницы, а также во время навигации по маршрутизатору, которая загружает больше данных и кода. Однако с точки зрения пользователя загрузка и рендеринг данных не рассказывают всю историю при рассмотрении вопроса о готовности нового контента. По умолчанию браузеры загружают таблицы стилей, шрифты и изображения независимо, что может привести к скачкам пользовательского интерфейса и последовательным сдвигам макета.

Мы работаем над полной интеграцией Suspense с жизненным циклом загрузки таблиц стилей, шрифтов и изображений, чтобы React учитывал их при определении готовности контента к отображению. Без каких-либо изменений в способе создания ваших компонентов React обновления будут вести себя более согласованно и приятно. В качестве оптимизации мы также предоставим ручной способ предварительной загрузки таких ресурсов, как шрифты, непосредственно из компонентов.

В настоящее время мы реализуем эти функции и скоро поделимся дополнительной информацией.

## Метаданные документа {/*document-metadata*/}

Разные страницы и экраны в вашем приложении могут иметь разные метаданные, такие как тег `<title>`, описание и другие теги `<meta>`, относящиеся к этому экрану. С точки зрения обслуживания, более масштабируемо хранить эту информацию рядом с компонентом React для этой страницы или экрана. Однако HTML-теги для этих метаданных должны находиться в `<head>` документа, который обычно отображается в компоненте в самом корне вашего приложения.

Сегодня люди решают эту проблему одним из двух способов.

Один из способов — отобразить специальный сторонний компонент, который перемещает `<title>`, `<meta>` и другие теги внутри него в `<head>` документа. Это работает для основных браузеров, но есть много клиентов, которые не запускают JavaScript на стороне клиента, например, парсеры Open Graph, поэтому этот метод не подходит для всех.

Другой способ — выполнить рендеринг страницы на сервере в двух частях. Сначала отображается основное содержимое, и собираются все такие теги. Затем отображается `<head>` с этими тегами. Наконец, `<head>` и основное содержимое отправляются в браузер. Этот подход работает, но он не позволяет вам воспользоваться [Streaming Server Renderer React 18](/reference/react-dom/server/renderToReadableStream), потому что вам придется ждать, пока весь контент не будет отображен, прежде чем отправлять `<head>`.

Вот почему мы добавляем встроенную поддержку рендеринга тегов `<title>`, `<meta>` и метаданных `<link>` в любом месте вашего дерева компонентов из коробки. Это будет работать одинаково во всех средах, включая полностью клиентский код, SSR и, в будущем, RSC. Мы скоро поделимся более подробной информацией об этом.

## React Optimizing Compiler {/*react-optimizing-compiler*/}

С момента нашего предыдущего обновления мы активно работали над дизайном [React Forget](/blog/2022/06/15/react-labs-what-we-have-been-working-on-june-2022#react-compiler), оптимизирующего компилятора для React. Ранее мы говорили о нем как об «автоматическом компиляторе мемоизации», и это верно в некотором смысле. Но создание компилятора помогло нам еще глубже понять модель программирования React. Лучший способ понять React Forget — это автоматический компилятор *реактивности*.

Основная идея React заключается в том, что разработчики определяют свой пользовательский интерфейс как функцию от текущего состояния. Вы работаете с обычными значениями JavaScript — числами, строками, массивами, объектами — и используете стандартные идиомы JavaScript — if/else, for и т. д. — для описания логики вашего компонента. Модель мышления заключается в том, что React будет перерендеривать всякий раз, когда изменяется состояние приложения. Мы считаем, что эта простая модель мышления и сохранение близости к семантике JavaScript является важным принципом в модели программирования React.

Подвох в том, что React иногда может быть *слишком* реактивным: он может перерендеривать слишком много. Например, в JavaScript у нас нет дешевых способов сравнить, эквивалентны ли два объекта или массива (имеют ли они одни и те же ключи и значения), поэтому создание нового объекта или массива при каждом рендеринге может привести к тому, что React сделает больше работы, чем ему строго необходимо. Это означает, что разработчики должны явно мемоизировать компоненты, чтобы не перереагировать на изменения.

Наша цель с React Forget — гарантировать, что приложения React по умолчанию имеют нужное количество реактивности: что приложения перерендериваются только тогда, когда значения состояния *значительно* изменяются. С точки зрения реализации это означает автоматическую мемоизацию, но мы считаем, что структура реактивности — лучший способ понять React и Forget. Один из способов думать об этом заключается в том, что React в настоящее время перерендеривает, когда изменяется идентичность объекта. С Forget React перерендеривает, когда изменяется семантическое значение, но без затрат времени выполнения на глубокие сравнения.

Что касается конкретного прогресса, то с момента нашего последнего обновления мы существенно переработали дизайн компилятора, чтобы согласовать его с этим подходом автоматической реактивности и включить отзывы об использовании компилятора внутри компании. После некоторых значительных рефакторингов компилятора, начавшихся в конце прошлого года, мы начали использовать компилятор в производстве в ограниченных областях в Meta. Мы планируем открыть его исходный код, как только докажем его в производстве.

Наконец, многие люди выразили заинтересованность в том, как работает компилятор. Мы с нетерпением ждем возможности поделиться гораздо большим количеством подробностей, когда мы докажем компилятор и откроем его исходный код. Но есть несколько моментов, которыми мы можем поделиться сейчас:

Ядро компилятора почти полностью отделено от Babel, а основной API компилятора (примерно) — старый AST на входе, новый AST на выходе (с сохранением данных о местоположении в исходном коде). Под капотом мы используем пользовательское представление кода и конвейер преобразования для выполнения низкоуровневого семантического анализа. Однако основным общедоступным интерфейсом для компилятора будет Babel и другие плагины системы сборки. Для простоты тестирования у нас в настоящее время есть плагин Babel, который представляет собой очень тонкую оболочку, которая вызывает компилятор для создания новой версии каждой функции и подмены ее.

Поскольку мы рефакторили компилятор в течение последних нескольких месяцев, мы хотели сосредоточиться на уточнении основной модели компиляции, чтобы убедиться, что мы можем справиться со сложностями, такими как условные операторы, циклы, переназначение и мутация. Однако в JavaScript есть много способов выразить каждую из этих функций: if/else, тернарные операторы, for, for-in, for-of и т. д. Попытка поддержать весь язык заранее задержала бы момент, когда мы смогли бы проверить основную модель. Вместо этого мы начали с небольшого, но репрезентативного подмножества языка: let/const, if/else, for циклы, объекты, массивы, примитивы, вызовы функций и несколько других функций. По мере того, как мы обретали уверенность в основной модели и уточняли наши внутренние абстракции, мы расширяли поддерживаемое подмножество языка. Мы также явно указываем синтаксис, который мы еще не поддерживаем, регистрируя диагностику и пропуская компиляцию для неподдерживаемого ввода. У нас есть утилиты, чтобы попробовать компилятор в кодовых базах Meta и посмотреть, какие неподдерживаемые функции являются наиболее распространенными, чтобы мы могли расставить приоритеты для них в первую очередь. Мы продолжим постепенно расширяться в сторону поддержки всего языка.

Чтобы сделать обычный JavaScript в компонентах React реактивным, требуется компилятор с глубоким пониманием семантики, чтобы он мог точно понимать, что делает код. Применяя этот подход, мы создаем систему реактивности в JavaScript, которая позволяет вам писать производственный код любой сложности с полной выразительностью языка, вместо того, чтобы ограничиваться предметно-ориентированным языком.

## Offscreen Rendering {/*offscreen-rendering*/}

Offscreen rendering — это предстоящая возможность в React для рендеринга экранов в фоновом режиме без дополнительных накладных расходов на производительность. Вы можете думать об этом как о версии свойства CSS [`content-visibility`](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility), которая работает не только для элементов DOM, но и для компонентов React. В ходе наших исследований мы обнаружили множество вариантов использования:

- Маршрутизатор может предварительно отображать экраны в фоновом режиме, чтобы они были мгновенно доступны, когда пользователь переходит к ним.
- Компонент переключения вкладок может сохранять состояние скрытых вкладок, чтобы пользователь мог переключаться между ними, не теряя свой прогресс.
- Виртуализированный компонент списка может предварительно отображать дополнительные строки над и под видимым окном.
- При открытии модального окна или всплывающего окна остальная часть приложения может быть переведена в «фоновый» режим, чтобы события и обновления были отключены для всего, кроме модального окна.

Большинство разработчиков React не будут напрямую взаимодействовать с API offscreen React. Вместо этого offscreen rendering будет интегрирован в такие вещи, как маршрутизаторы и библиотеки пользовательского интерфейса, а затем разработчики, которые используют эти библиотеки, автоматически получат выгоду без дополнительной работы.

Идея состоит в том, что вы должны иметь возможность отображать любое дерево React за пределами экрана, не изменяя способ написания ваших компонентов. Когда компонент отображается за пределами экрана, он на самом деле не *монтируется*, пока компонент не станет видимым — его эффекты не запускаются. Например, если компонент использует `useEffect` для регистрации аналитики при первом появлении, предварительный рендеринг не испортит точность этой аналитики. Аналогичным образом, когда компонент переходит за пределы экрана, его эффекты также размонтируются. Ключевой особенностью offscreen rendering является то, что вы можете переключать видимость компонента, не теряя его состояния.

С момента нашего последнего обновления мы протестировали экспериментальную версию предварительного рендеринга внутри Meta в наших приложениях React Native на Android и iOS с положительными результатами производительности. Мы также улучшили работу offscreen rendering с Suspense — приостановка внутри дерева за пределами экрана не вызовет fallbacks Suspense. Наша оставшаяся работа включает в себя доработку примитивов, которые предоставляются разработчикам библиотек. Мы планируем опубликовать RFC позже в этом году, а также экспериментальный API для тестирования и обратной связи.

## Transition Tracing {/*transition-tracing*/}

API Transition Tracing позволяет вам обнаруживать, когда [React Transitions](/reference/react/useTransition) становятся медленнее, и выяснять, почему они могут быть медленными. После нашего последнего обновления мы завершили первоначальный дизайн API и опубликовали [RFC](https://github.com/reactjs/rfcs/pull/238). Основные возможности также были реализованы. В настоящее время проект приостановлен. Мы приветствуем отзывы по RFC и надеемся возобновить его разработку, чтобы предоставить лучший инструмент измерения производительности для React. Это будет особенно полезно с маршрутизаторами, построенными на основе React Transitions, такими как [Next.js App Router](/learn/start-a-new-react-project#nextjs-app-router).
