Мы также предоставляем документацию для случаев, когда фреймворк не подходит для вашего проекта, вы хотите создать свой собственный фреймворк или просто хотите узнать, как работает React, [создав приложение React с нуля](/learn/build-a-react-app-from-scratch).

</Intro>

Когда мы выпустили Create React App в 2016 году, не было явного способа создать новое приложение React.

Чтобы создать приложение React, вам приходилось устанавливать кучу инструментов и настраивать их самостоятельно для поддержки базовых функций, таких как JSX, линтинг и горячая перезагрузка. Это было очень сложно сделать правильно, поэтому [сообщество](https://github.com/react-boilerplate/react-boilerplate) [создавало](https://github.com/kriasoft/react-starter-kit) [стартовые наборы](https://github.com/petehunt/react-boilerplate) для [распространённых](https://github.com/gaearon/react-hot-boilerplate) [конфигураций](https://github.com/erikras/react-redux-universal-hot-example). Однако стартовые наборы было сложно обновлять, а фрагментация мешала React выпускать новые функции.

Create React App решил эти проблемы, объединив несколько инструментов в одну рекомендуемую конфигурацию. Это позволило приложениям простым способом обновляться до новых инструментальных функций и позволило команде React развертывать нетривиальные изменения в инструментарии (поддержка Fast Refresh, правила линтинга для React Hooks) для самой широкой аудитории.

Эта модель стала настолько популярной, что сегодня существует целая категория инструментов, работающих таким образом.

## Прекращение поддержки Create React App {/*deprecating-create-react-app*/}

Хотя Create React App упрощает начало работы, [существует несколько ограничений](#limitations-of-build-tools), которые затрудняют создание высокопроизводительных продакшен-приложений. В принципе, мы могли бы решить эти проблемы, по сути, превратив его во [фреймворк](#why-we-recommend-frameworks).

Однако, поскольку у Create React App в настоящее время нет активных сопровождающих, и уже существует множество фреймворков, решающих эти проблемы, мы решили прекратить поддержку Create React App.

Начиная с сегодняшнего дня, при установке нового приложения вы увидите предупреждение о прекращении поддержки:

<ConsoleBlockMulti>
<ConsoleLogLine level="error">

create-react-app устарел.
{'\n\n'}
Список актуальных фреймворков React вы можете найти на react.dev
Подробнее см.: react.dev/link/cra
{'\n\n'}
Это сообщение об ошибке будет показано только один раз за установку.

</ConsoleLogLine>
</ConsoleBlockMulti>

Мы также добавили уведомление о прекращении поддержки на [веб-сайт](https://create-react-app.dev/) Create React App и в [репозиторий](https://github.com/facebook/create-react-app) на GitHub. Create React App продолжит работать в режиме поддержки, и мы опубликовали новую версию Create React App для работы с React 19.

## Как мигрировать на фреймворк {/*how-to-migrate-to-a-framework*/}
Мы рекомендуем [создавать новые приложения React](/learn/creating-a-react-app) с использованием фреймворка. Все рекомендуемые нами фреймворки поддерживают рендеринг на стороне клиента ([CSR](https://developer.mozilla.org/en-US/docs/Glossary/CSR)) и одностраничные приложения ([SPA](https://developer.mozilla.org/en-US/docs/Glossary/SPA)), и могут быть развернуты на CDN или статических хостингах без сервера.

Для существующих приложений эти руководства помогут вам мигрировать на SPA, работающее только на стороне клиента:

* [Руководство по миграции с Create React App для Next.js](https://nextjs.org/docs/app/building-your-application/upgrading/from-create-react-app)
* [Руководство по переходу на фреймворк от React Router](https://reactrouter.com/upgrading/component-routes).
* [Руководство по миграции с Expo webpack на Expo Router](https://docs.expo.dev/router/migrate/from-expo-webpack/)

## Как мигрировать на сборщик {/*how-to-migrate-to-a-build-tool*/}

Если ваше приложение имеет необычные ограничения, или вы предпочитаете решать эти проблемы, создавая свой собственный фреймворк, или просто хотите узнать, как React работает с нуля, вы можете создать собственную пользовательскую конфигурацию с React, используя Vite, Parcel или Rsbuild.

Для существующих приложений эти руководства помогут вам мигрировать на сборщик:

#### Нужен ли мне фреймворк? {/*do-i-need-a-framework*/}

Большинство приложений выиграют от использования фреймворка, но существуют веские причины для создания приложения React с нуля. Хорошим эмпирическим правилом является то, что если вашему приложению требуется маршрутизация, вы, вероятно, выиграете от использования фреймворка.

Подобно тому, как Svelte имеет Sveltekit, Vue имеет Nuxt, а Solid имеет SolidStart, [React рекомендует использовать фреймворк](#why-we-recommend-frameworks), который полностью интегрирует маршрутизацию с такими функциями, как получение данных и разделение кода "из коробки". Это позволяет избежать необходимости писать собственные сложные конфигурации и, по сути, создавать фреймворк самостоятельно.

Однако вы всегда можете [создать приложение React с нуля](/learn/build-a-react-app-from-scratch), используя сборщик, такой как Vite, Parcel или Rsbuild.

</DeepDive>

Продолжайте читать, чтобы узнать больше об [ограничениях сборщиков](#limitations-of-build-tools) и о том, [почему мы рекомендуем фреймворки](#why-we-recommend-frameworks).

## Ограничения инструментов сборки {/*limitations-of-build-tools*/}

Create React App и подобные инструменты сборки упрощают начало работы над React-приложением. После выполнения команды `npx create-react-app my-app` вы получаете полностью настроенное React-приложение с сервером разработки, линтером и сборкой для продакшена.

Например, если вы создаёте внутренний инструмент администрирования, вы можете начать с главной страницы:

```js
export default function App() {
  return (
    <div>
      <h1>Добро пожаловать в инструмент администрирования!</h1>
    </div>
  )
}
```

Это позволяет вам немедленно начать писать код на React с такими функциями, как JSX, стандартные правила линтера и сборщик для работы как в режиме разработки, так и в продакшене. Однако в этой конфигурации отсутствуют инструменты, необходимые для создания реального продакшн-приложения.

Большинству продакшн-приложений требуются решения для таких задач, как маршрутизация, получение данных и разделение кода.

### Маршрутизация {/*routing*/}

Create React App не включает в себя конкретного решения для маршрутизации. Если вы только начинаете, один из вариантов — использовать `useState` для переключения между маршрутами. Но это означает, что вы не сможете делиться ссылками на ваше приложение — каждая ссылка будет вести на одну и ту же страницу — и со временем структура вашего приложения станет сложной:

```js
import {useState} from 'react';

import Home from './Home';
import Dashboard from './Dashboard';

export default function App() {
  // ❌ Маршрутизация в состоянии не создает URL
  const [route, setRoute] = useState('home');
  return (
    <div>
      {route === 'home' && <Home />}
      {route === 'dashboard' && <Dashboard />}
    </div>
  )
}
```

Именно поэтому большинство приложений, использующих Create React App, решают проблему маршрутизации с помощью библиотеки маршрутизации, такой как [React Router](https://reactrouter.com/) или [Tanstack Router](https://tanstack.com/router/latest). С библиотекой маршрутизации вы можете добавлять дополнительные маршруты в приложение, что определяет структуру вашего приложения и позволяет начать делиться ссылками на маршруты. Например, с React Router вы можете определить маршруты:

```js
import {RouterProvider, createBrowserRouter} from 'react-router';

import Home from './Home';
import Dashboard from './Dashboard';

// ✅ У каждого маршрута свой URL
const router = createBrowserRouter([
  {path: '/', element: <Home />},
  {path: '/dashboard', element: <Dashboard />}
]);

export default function App() {
  return (
    <RouterProvider value={router} />
  )
}
```

С этим изменением вы можете поделиться ссылкой на `/dashboard`, и приложение перейдёт на страницу панели управления. После установки библиотеки маршрутизации вы сможете добавлять дополнительные функции, такие как вложенные маршруты, защищённые маршруты и переходы между маршрутами, которые сложно реализовать без библиотеки маршрутизации.

Здесь происходит компромисс: библиотека маршрутизации добавляет сложности в приложение, но также предоставляет функции, которые сложно реализовать без неё.

### Получение данных {/*data-fetching*/}

Ещё одна распространённая проблема в Create React App — получение данных. Create React App не включает в себя конкретного решения для получения данных. Если вы только начинаете, распространённый вариант — использовать `fetch` в эффекте для загрузки данных.

Но это означает, что данные загружаются после рендеринга компонента, что может привести к сетевым водопадам. Сетевые водопады возникают из-за загрузки данных во время рендеринга приложения вместо параллельной загрузки во время скачивания кода:

```js
export default function Dashboard() {
  const [data, setData] = useState(null);

  // ❌ Получение данных в компоненте вызывает сетевые водопады
  useEffect(() => {
    fetch('/api/data')
      .then(response => response.json())
      .then(data => setData(data));
  }, []);

  return (
    <div>
      {data.map(item => <div key={item.id}>{item.name}</div>)}
    </div>
  )
}
```

Получение данных в эффекте означает, что пользователю приходится дольше ждать, чтобы увидеть контент, даже если данные могли быть загружены раньше. Чтобы решить эту проблему, вы можете использовать библиотеку для получения данных, такую как [React Query](https://react-query.tanstack.com/), [SWR](https://swr.vercel.app/), [Apollo](https://www.apollographql.com/docs/react) или [Relay](https://relay.dev/), которые предоставляют возможности для предварительной загрузки данных, чтобы запрос начинался до рендеринга компонента.

Эти библиотеки лучше всего работают при интеграции с вашим шаблоном "загрузчика" маршрутизации для определения зависимостей данных на уровне маршрута, что позволяет маршрутизатору оптимизировать получение данных:

```js
export async function loader() {
  const response = await fetch(`/api/data`);
  const data = await response.json();
  return data;
}

// ✅ Получение данных параллельно во время скачивания кода
export default function Dashboard({loaderData}) {
  return (
    <div>
      {loaderData.map(item => <div key={item.id}>{item.name}</div>)}
    </div>
  )
}
```

При первоначальной загрузке маршрутизатор может немедленно получить данные перед рендерингом маршрута. Когда пользователь перемещается по приложению, маршрутизатор может одновременно получать как данные, так и код маршрута, параллельно выполняя запросы. Это сокращает время, необходимое для отображения контента на экране, и может улучшить пользовательский опыт.

Однако это требует правильной настройки загрузчиков в вашем приложении и сопряжено с увеличением сложности ради повышения производительности.

### Разделение кода {/*code-splitting*/}

Ещё одна распространённая проблема в Create React App — [разделение кода](https://www.patterns.dev/vanilla/bundle-splitting). Create React App не включает в себя конкретного решения для разделения кода. Если вы только начинаете, вы можете вообще не задумываться о разделении кода.

Это означает, что ваше приложение поставляется как один пакет:

```txt
- bundle.js    75kb
```

Но для идеальной производительности вы должны "разделить" свой код на отдельные пакеты, чтобы пользователю нужно было загружать только то, что ему необходимо. Это сокращает время, которое пользователь должен ждать для загрузки вашего приложения, загружая только тот код, который ему нужен для просмотра текущей страницы.

```txt
- core.js      25kb
- home.js      25kb
- dashboard.js 25kb
```

Один из способов разделения кода — использовать `React.lazy`. Однако это означает, что код не загружается до тех пор, пока компонент не будет отрендерен, что может привести к сетевым водопадам. Более оптимальным решением является использование функции маршрутизатора, которая загружает код параллельно во время скачивания кода. Например, React Router предоставляет опцию `lazy` для указания того, что маршрут должен быть разделён по коду, и оптимизации времени его загрузки:

```js
import Home from './Home';
import Dashboard from './Dashboard';

// ✅ Маршруты загружаются до рендеринга
const router = createBrowserRouter([
  {path: '/', lazy: () => import('./Home')},
  {path: '/dashboard', lazy: () => import('Dashboard')}
]);
```

Оптимизированное разделение кода — сложная задача, и легко допустить ошибки, которые могут привести к тому, что пользователь загрузит больше кода, чем ему нужно. Оно лучше всего работает при интеграции с вашим маршрутизатором и решениями для загрузки данных, чтобы максимизировать кеширование, параллелизовать запросы и поддерживать шаблоны ["импорт по взаимодействию"](https://www.patterns.dev/vanilla/import-on-interaction).

### И многое другое... {/*and-more*/}

Это лишь несколько примеров ограничений Create React App.

После интеграции маршрутизации, получения данных и разделения кода вам также необходимо учитывать состояния ожидания, прерывания навигации, сообщения об ошибках для пользователя и повторную проверку данных. Существуют целые категории проблем, которые пользователям необходимо решать, такие как:

<div style={{display: 'flex', width: '100%', justifyContent: 'space-around'}}>
  <ul>
    <li>Доступность</li>
    <li>Загрузка ресурсов</li>
    <li>Аутентификация</li>
    <li>Кеширование</li>
  </ul>
  <ul>
    <li>Обработка ошибок</li>
    <li>Изменение данных</li>
    <li>Навигация</li>
    <li>Оптимистичные обновления</li>
  </ul>
  <ul>
    <li>Прогрессивное улучшение</li>
    <li>Рендеринг на стороне сервера</li>
    <li>Генерация статических сайтов</li>
    <li>Потоковая передача</li>
  </ul>
</div>

Все эти аспекты работают вместе, чтобы создать наиболее оптимальную [последовательность загрузки](https://www.patterns.dev/vanilla/loading-sequence).

Решение каждой из этих проблем по отдельности в Create React App может быть сложным, поскольку каждая проблема взаимосвязана с другими и может потребовать глубоких знаний в областях, с которыми пользователи могут быть не знакомы. Чтобы решить эти проблемы, пользователи в конечном итоге создают свои собственные индивидуальные решения поверх Create React App, что и было проблемой, которую изначально пытался решить Create React App.

## Почему мы рекомендуем фреймворки {/*why-we-recommend-frameworks*/}

Хотя вы могли бы самостоятельно решить все эти задачи с помощью инструмента сборки, такого как Create React App, Vite или Parcel, сделать это хорошо сложно. Точно так же, как Create React App сам интегрировал несколько инструментов сборки, вам нужен инструмент, который объединит все эти возможности для обеспечения наилучшего пользовательского опыта.

Эта категория инструментов, которые интегрируют инструменты сборки, рендеринг, маршрутизацию, получение данных и разделение кода, известна как «фреймворки» — или, если вы предпочитаете называть сам React фреймворком, вы можете назвать их «метафреймворками».

Фреймворки навязывают некоторые мнения о структурировании вашего приложения, чтобы обеспечить гораздо лучший пользовательский опыт, так же, как инструменты сборки навязывают некоторые мнения, чтобы упростить работу с инструментами. Вот почему мы начали рекомендовать фреймворки, такие как [Next.js](https://nextjs.org/), [React Router](https://reactrouter.com/) и [Expo](https://expo.dev/) для новых проектов.

Фреймворки предоставляют такой же опыт начала работы, как и Create React App, но также предлагают решения проблем, которые пользователи в любом случае должны решать в реальных продакшен-приложениях.

<DeepDive>

#### Серверный рендеринг — это необязательно {/*server-rendering-is-optional*/}

Рекомендуемые нами фреймворки предоставляют возможность создавать приложение с [клиентским рендерингом (CSR)](https://developer.mozilla.org/ru/docs/Glossary/CSR).

В некоторых случаях CSR — правильный выбор для страницы, но во многих случаях это не так. Даже если большая часть вашего приложения рендерится на клиенте, часто есть отдельные страницы, которые могут выиграть от серверного рендеринга, такого как [генерация статических сайтов (SSG)](https://developer.mozilla.org/ru/docs/Glossary/SSG) или [серверный рендеринг (SSR)](https://developer.mozilla.org/ru/docs/Glossary/SSR), например, страница условий обслуживания или документация.

Серверный рендеринг обычно отправляет меньше JavaScript клиенту и полный HTML-документ, что обеспечивает более быструю [первую отрисовку контента (FCP)](https://web.dev/articles/fcp), уменьшая [общее время блокировки (TBT)](https://web.dev/articles/tbt), что также может снизить [время до следующей отрисовки (INP)](https://web.dev/articles/inp). Именно поэтому [команда Chrome призвала](https://web.dev/articles/rendering-on-the-web) разработчиков рассмотреть статический или серверный рендеринг вместо полного клиентского подхода для достижения наилучшей возможной производительности.

Использование сервера сопряжено с компромиссами, и это не всегда лучший вариант для каждой страницы. Генерация страниц на сервере влечет за собой дополнительные расходы и время на генерацию, что может увеличить [время до первого байта (TTFB)](https://web.dev/articles/ttfb). Наиболее производительные приложения способны выбирать правильную стратегию рендеринга для каждой страницы, основываясь на компромиссах каждой стратегии.

Фреймворки предоставляют возможность использовать сервер на любой странице, если вы этого хотите, но не заставляют вас использовать сервер. Это позволяет вам выбирать правильную стратегию рендеринга для каждой страницы в вашем приложении.

#### А как насчет Server Components {/*server-components*/}

Рекомендуемые нами фреймворки также включают поддержку React Server Components.

Server Components помогают решить эти проблемы, перенося маршрутизацию и получение данных на сервер, и позволяя выполнять разделение кода для клиентских компонентов на основе данных, которые вы рендерите, а не только маршрута, и уменьшая объем JavaScript, отправляемого для наилучшей возможной [последовательности загрузки](https://www.patterns.dev/vanilla/loading-sequence).

Server Components не требуют сервера. Они могут быть запущены во время сборки на вашем CI-сервере для создания приложения с генерацией статических сайтов (SSG) или во время выполнения на веб-сервере для приложения с серверным рендерингом (SSR).

См. [Introducing zero-bundle size React Server Components](/blog/2020/12/21/data-fetching-with-react-server-components) и [документацию](/reference/rsc/server-components) для получения дополнительной информации.

</DeepDive>

<Note>

#### Серверный рендеринг — это не только для SEO {/*server-rendering-is-not-just-for-seo*/}

Распространенное заблуждение заключается в том, что серверный рендеринг нужен только для [SEO](https://developer.mozilla.org/ru/docs/Glossary/SEO).

Хотя серверный рендеринг может улучшить SEO, он также улучшает производительность, уменьшая объем JavaScript, который пользователю необходимо загрузить и разобрать, прежде чем он сможет увидеть контент на экране.

Именно поэтому команда Chrome [призвала](https://web.dev/articles/rendering-on-the-web) разработчиков рассмотреть статический или серверный рендеринг вместо полного клиентского подхода для достижения наилучшей возможной производительности.

</Note>
