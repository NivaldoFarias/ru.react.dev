  ## Общие правила


  - _Вы_ и его производные пишите с маленькой буквы

  - Всегда используйте букву `ё` (это легко соблюдать с помощью [данного
  npm-пакета](https://github.com/hcodes/eyo))

  - Используйте тире вместо дефиса (оно должно быть намного длиннее, чем дефис).
  Тире: `—`, дефис: `-`

  - Переводите комментарии в примерах кода, но не содержимое

  - Используйте терминологию [словаря
  «Веб-стандартов»](https://github.com/web-standards-ru/dictionary), если нет
  исходного варианта в таблице ниже

  - Ссылки на ресурсы (MDN, Wikipedia) должны вести на русскую версию, если есть
  соответствующий перевод.

  - Иностранные имена переводите с указанием оригинального имени в скобках: _Дэн
  Абрамов (Dan Abramov)_. При этом обязательно проверьте уже существующий
  перевод имени в [словаре имён
  «Веб-стандартов»](https://github.com/web-standards-ru/dictionary/blob/master/\
  names.md)

  - Не переводите наименования компаний (Facebook, Airbnb), библиотек (Jest,
  Enzyme) и т.д.

  - Не переводите аббревиатуры (API, DOM, HOC, UI).

  - Исключайте отсылки на пол читателя (см. секцию 3 на [этой
  странице](http://www.un.org/ru/gender-inclusive-language/guidelines.shtml))

  - Названия статей и заголовки пишутся с одной заглавной буквы («Компоненты и
  пропсы», не «Компоненты и Пропсы»).


  ### Слово живое и мёртвое


  Прежде чем переводить, почитайте пару страниц из «Слова живого и мёртвого»
  Норы Галь. Хотя бы эти две:


  * [Берегись канцелярита!](http://www.vavilon.ru/noragal/slovo2.html)

  * [Словесная алгебра](http://www.vavilon.ru/noragal/slovo4.html)


  **По мере возможности, избегайте отглагольных существительных!**


  * **Деревянно:** *для открытия*

  * **Живо:** *чтобы открыть*


  **Также избегайте пассивного залога:**


  * **Деревянно:** *будет рассказано*

  * **Живо:** *мы узнаем*


  **Предпочитайте простые слова (за исключением терминологии ниже):**


  * **Деревянно:** *демонстрирует*

  * **Живо:** *показывает*


  Чтобы избежать кальки, можно брать смысл предложения, а потом перефразировать
  так, как объясняли бы старшему коллеге. Если предложение звучит нелепо вслух,
  то его надо переписать. Например:


  **Оригинал:** *React has been designed from the start for gradual adoption,
  and you can use as little or as much React as you need.*


  **Мёртвая калька:** *React был спроектирован с самого начала для постепенного
  внедрения, и вы можете использовать столько React, сколько вам нужно.*


  **Нормальный перевод:** *Чтобы внедрить React, не надо ничего переписывать.
  Его можно использовать как для маленькой кнопки, так и для целого приложения.*


  Небольшие вольности в переводе допускаются, но только если они помогают
  передать смысл. Перевод не должен быть ни деревянным, ни фамильярным. Истина
  где-то посередине.

  ### Идентификаторы заголовков


  Каждый заголовок имеет явный идентификатор:


  ```md

  ## Try React {#try-react}

  ```


  **НЕ** переводите такие идентификаторы! Они используются для навигации.
  Изменение идентификатора неизбежно приведёт к поломке, если на документ
  ссылкаются извне, например так:


  ```md

  Прочтите [главу для начинающих](/getting-started#try-react), чтобы узнать
  больше.

  ```


  ✅ Можно:


  ```md

  ## Попробуйте React {#try-react}

  ```


  ❌ НЕЛЬЗЯ:


  ```md

  ## Попробуйте React {#попробуйте-react}

  ```


  Это сломает ссылку, приведённую в примере выше.


  ### Текст в блоках кода


  Не переводите текст в блоках кода, кроме комментариев. А вот комментарии и
  текст в строках следует переводить, если они не относятся к коду.


  Пример:

  ```js

  // Example

  const element = <h1>Hello, world</h1>;

  ReactDOM.render(element, document.getElementById('root'));

  ```


  ✅ МОЖНО:


  ```js

  // Пример

  const element = <h1>Hello, world</h1>;

  ReactDOM.render(element, document.getElementById('root'));

  ```


  ✅ ТОЖЕ МОЖНО:


  ```js

  // Пример

  const element = <h1>Здравствуй, мир!</h1>;

  ReactDOM.render(element, document.getElementById('root'));

  ```


  ❌ НЕЛЬЗЯ:


  ```js

  // Пример

  const element = <h1>Здравствуй, мир!</h1>;

  // \"root\" ссылается на идентификатор элемента.

  // Не переводите его!

  ReactDOM.render(element, document.getElementById('корень'));

  ```


  ❌ СОВСЕМ НЕЛЬЗЯ:


  ```js

  // Пример

  пост элемент = <з1>Здравствуй, мир!</з1>;

  РеактДОМ.отрендери(элемент, документ.получиЭлементПоАйди('корень'));

  ```


  ### Внешние ссылки


  Если внешняя ссылка ведёт к статье на [MDN] или [Wikipedia], и там существует
  статья на русском языке, исправьте ссылку, чтобы она указывала на русский
  вариант, даже если он неполный или требует улучшения.


  [MDN]: https://developer.mozilla.org/en-US/

  [Wikipedia]: https://en.wikipedia.org/wiki/Main_Page


  Пример:


  ```md

  React elements are
  [immutable](https://en.wikipedia.org/wiki/Immutable_object).

  ```


  ✅ OK:


  ```md

  Элементы React
  [иммутабельны](https://ru.wikipedia.org/wiki/%D0%9D%D0%B5%D0%B8%D0%B7%D0%BC%D\
  0%B5%D0%BD%D1%8F%D0%B5%D0%BC%D1%8B%D0%B9_%D0%BE%D0%B1%D1%8A%D0%B5%D0%BA%D1%82\
  ).

  ```


  Для ссылок, у которых нету языковых эквивалентов (Stack Overflow, видео на
  YouTube, и т. д.), просто оставьте оригинальный вариант как есть.

Когда мы выпустили Create React App в 2016 году, не было четкого способа создать новое приложение React.

Чтобы создать приложение React, вам нужно было установить кучу инструментов и связать их вместе, чтобы поддерживать основные функции, такие как JSX, линтинг и горячая перезагрузка. Это было очень сложно сделать правильно, поэтому [сообщество](https://github.com/react-boilerplate/react-boilerplate) [создало](https://github.com/kriasoft/react-starter-kit) [шаблоны](https://github.com/petehunt/react-boilerplate) для [распространенных](https://github.com/gaearon/react-hot-boilerplate) [настроек](https://github.com/erikras/react-redux-universal-hot-example). Однако шаблоны было сложно обновлять, а фрагментация затрудняла выпуск новых функций React.

Create React App решил эти проблемы, объединив несколько инструментов в единую рекомендуемую конфигурацию. Это позволило приложениям простым способом обновляться до новых функций инструментов и позволило команде React развертывать нетривиальные изменения инструментов (поддержка Fast Refresh, правила линтинга React Hooks) для максимально широкой аудитории.

Эта модель стала настолько популярной, что сегодня существует целая категория инструментов, работающих таким образом.

#### Нужен ли мне фреймворк? {/*do-i-need-a-framework*/}

Большинство приложений выиграют от использования фреймворка, но есть веские причины для создания приложения React с нуля. Хорошее эмпирическое правило: если вашему приложению требуется маршрутизация, вам, вероятно, будет полезен фреймворк.

Точно так же, как у Svelte есть Sveltekit, у Vue есть Nuxt, а у Solid есть SolidStart, [React рекомендует использовать фреймворк](#why-we-recommend-frameworks), который полностью интегрирует маршрутизацию в такие функции, как получение данных и разделение кода, прямо из коробки. Это позволяет избежать необходимости писать собственные сложные конфигурации и, по сути, создавать фреймворк самостоятельно.

Однако вы всегда можете [создать приложение React с нуля](/learn/build-a-react-app-from-scratch), используя такой инструмент сборки, как Vite, Parcel или Rsbuild.

</DeepDive>

## Ограничения инструментов сборки {/*limitations-of-build-tools*/}

Create React App и подобные инструменты сборки упрощают начало работы над созданием приложения React. После запуска `npx create-react-app my-app` вы получаете полностью настроенное приложение React с сервером разработки, линтингом и рабочей сборкой.

Например, если вы создаете внутренний инструмент администрирования, вы можете начать с целевой страницы:

```js
export default function App() {
  return (
    <div>
      <h1>Welcome to the Admin Tool!</h1>
    </div>
  )
}
```

Это позволяет вам сразу же начать кодировать на React с такими функциями, как JSX, правила линтинга по умолчанию и бандлер для запуска как в разработке, так и в продакшене. Однако в этой настройке отсутствуют инструменты, необходимые для создания реального рабочего приложения.

Большинству рабочих приложений нужны решения для таких проблем, как маршрутизация, получение данных и разделение кода.

### Маршрутизация {/*routing*/}

Create React App не включает в себя конкретное решение для маршрутизации. Если вы только начинаете, один из вариантов — использовать `useState` для переключения между маршрутами. Но это означает, что вы не можете делиться ссылками на свое приложение — каждая ссылка будет вести на одну и ту же страницу — и структурировать свое приложение со временем становится сложно:

```js
import {useState} from 'react';

import Home from './Home';
import Dashboard from './Dashboard';

export default function App() {
  // ❌ Маршрутизация в состоянии не создает URL-адреса
  const [route, setRoute] = useState('home');
  return (
    <div>
      {route === 'home' && <Home />}
      {route === 'dashboard' && <Dashboard />}
    </div>
  )
}
```

Вот почему большинство приложений, использующих Create React App, решают добавить маршрутизацию с помощью такой библиотеки маршрутизации, как [React Router](https://reactrouter.com/) или [Tanstack Router](https://tanstack.com/router/latest). С помощью библиотеки маршрутизации вы можете добавить дополнительные маршруты в приложение, что дает представление о структуре вашего приложения и позволяет вам начать делиться ссылками на маршруты. Например, с помощью React Router вы можете определить маршруты:

```js
import {RouterProvider, createBrowserRouter} from 'react-router';

import Home from './Home';
import Dashboard from './Dashboard';

// ✅ У каждого маршрута свой URL-адрес
const router = createBrowserRouter([
  {path: '/', element: <Home />},
  {path: '/dashboard', element: <Dashboard />}
]);

export default function App() {
  return (
    <RouterProvider value={router} />
  )
}
```

С этим изменением вы можете поделиться ссылкой на `/dashboard`, и приложение перейдет на страницу панели управления. После того, как у вас есть библиотека маршрутизации, вы можете добавить дополнительные функции, такие как вложенные маршруты, охранники маршрутов и переходы между маршрутами, которые сложно реализовать без библиотеки маршрутизации.

Здесь делается компромисс: библиотека маршрутизации добавляет сложность в приложение, но также добавляет функции, которые сложно реализовать без нее.

### Получение данных {/*data-fetching*/}

Еще одна распространенная проблема в Create React App — получение данных. Create React App не включает в себя конкретное решение для получения данных. Если вы только начинаете, распространенным вариантом является использование `fetch` в эффекте для загрузки данных.

Но это означает, что данные извлекаются после рендеринга компонента, что может вызвать сетевые водопады. Сетевые водопады вызваны извлечением данных при рендеринге вашего приложения, а не параллельно во время загрузки кода:

```js
export default function Dashboard() {
  const [data, setData] = useState(null);

  // ❌ Получение данных в компоненте вызывает сетевые водопады
  useEffect(() => {
    fetch('/api/data')
      .then(response => response.json())
      .then(data => setData(data));
  }, []);

  return (
    <div>
      {data.map(item => <div key={item.id}>{item.name}</div>)}
    </div>
  )
}
```

Получение данных в эффекте означает, что пользователю придется дольше ждать, чтобы увидеть контент, хотя данные можно было бы получить раньше. Чтобы решить эту проблему, вы можете использовать библиотеку получения данных, такую как [React Query](https://react-query.tanstack.com/), [SWR](https://swr.vercel.app/), [Apollo](https://www.apollographql.com/docs/react) или [Relay](https://relay.dev/), которые предоставляют возможности предварительной загрузки данных, чтобы запрос начинался до рендеринга компонента.

Эти библиотеки лучше всего работают при интеграции с вашим шаблоном «загрузчика» маршрутизации для указания зависимостей данных на уровне маршрута, что позволяет маршрутизатору оптимизировать получение ваших данных:

```js
export async function loader() {
  const response = await fetch(`/api/data`);
  const data = await response.json();
  return data;
}

// ✅ Получение данных параллельно во время загрузки кода
export default function Dashboard({loaderData}) {
  return (
    <div>
      {loaderData.map(item => <div key={item.id}>{item.name}</div>)}
    </div>
  )
}
```

При первоначальной загрузке маршрутизатор может получить данные сразу перед рендерингом маршрута. По мере того, как пользователь перемещается по приложению, маршрутизатор может получать как данные, так и маршрут одновременно, параллелизуя получение. Это сокращает время, необходимое для отображения контента на экране, и может улучшить взаимодействие с пользователем.

Однако это требует правильной настройки загрузчиков в вашем приложении и компромисса между сложностью и производительностью.

### Разделение кода {/*code-splitting*/}

Еще одна распространенная проблема в Create React App — [разделение кода](https://www.patterns.dev/vanilla/bundle-splitting). Create React App не включает в себя конкретное решение для разделения кода. Если вы только начинаете, вы можете вообще не рассматривать разделение кода.

Это означает, что ваше приложение поставляется в виде одного пакета:

```txt
- bundle.js    75kb
```

Но для идеальной производительности вам следует «разделить» свой код на отдельные пакеты, чтобы пользователю нужно было загружать только то, что ему нужно. Это уменьшает время, которое пользователю нужно ждать для загрузки вашего приложения, загружая только код, необходимый для просмотра страницы, на которой он находится.

```txt
- core.js      25kb
- home.js      25kb
- dashboard.js 25kb
```

Один из способов разделения кода — с помощью `React.lazy`. Однако это означает, что код не извлекается до тех пор, пока компонент не будет отрисован, что может вызвать сетевые водопады. Более оптимальное решение — использовать функцию маршрутизатора, которая извлекает код параллельно во время загрузки кода. Например, React Router предоставляет опцию `lazy`, чтобы указать, что маршрут должен быть разделен на код и оптимизировать его загрузку:

```js
import Home from './Home';
import Dashboard from './Dashboard';

// ✅ Маршруты загружаются перед рендерингом
const router = createBrowserRouter([
  {path: '/', lazy: () => import('./Home')},
  {path: '/dashboard', lazy: () => import('Dashboard')}
]);
```

Оптимизированное разделение кода сложно реализовать правильно, и легко допустить ошибки, которые могут привести к тому, что пользователь загрузит больше кода, чем ему нужно. Оно лучше всего работает при интеграции с вашим маршрутизатором и решениями для загрузки данных, чтобы максимизировать кэширование, параллелизовать получение и поддерживать шаблоны ["импорта по взаимодействию"](https://www.patterns.dev/vanilla/import-on-interaction).

## Почему мы рекомендуем фреймворки {/*why-we-recommend-frameworks*/}

Хотя вы могли бы решить все эти задачи самостоятельно в инструменте сборки, таком как Create React App, Vite или Parcel, это сложно сделать хорошо. Точно так же, как Create React App интегрировал несколько инструментов сборки вместе, вам нужен инструмент для интеграции всех этих функций, чтобы обеспечить наилучший опыт для пользователей.

Эта категория инструментов, которая объединяет инструменты сборки, рендеринг, маршрутизацию, получение данных и разделение кода, известна как «фреймворки» — или, если вы предпочитаете называть сам React фреймворком, вы можете называть их «метафреймворками».

Фреймворки навязывают некоторые мнения о структурировании вашего приложения, чтобы обеспечить гораздо лучший пользовательский опыт, так же, как инструменты сборки навязывают некоторые мнения, чтобы упростить работу с инструментами. Вот почему мы начали рекомендовать фреймворки, такие как [Next.js](https://nextjs.org/), [React Router](https://reactrouter.com/) и [Expo](https://expo.dev/) для новых проектов.

Фреймворки обеспечивают тот же опыт начала работы, что и Create React App, но также предоставляют решения проблем, которые пользователям все равно нужно решать в реальных рабочих приложениях.

#### Рендеринг на сервере — это опционально {/*server-rendering-is-optional*/}

Фреймворки, которые мы рекомендуем, предоставляют возможность создания приложения с [рендерингом на стороне клиента (CSR)](https://developer.mozilla.org/ru/docs/Glossary/CSR).

В некоторых случаях CSR — правильный выбор для страницы, но во многих случаях это не так. Даже если большая часть вашего приложения находится на стороне клиента, часто есть отдельные страницы, которые могут выиграть от функций рендеринга на сервере, таких как [генерация статического сайта (SSG)](https://developer.mozilla.org/ru/docs/Glossary/SSG) или [рендеринг на стороне сервера (SSR)](https://developer.mozilla.org/ru/docs/Glossary/SSR), например, страница с условиями обслуживания или документация.

Рендеринг на сервере обычно отправляет меньше JavaScript клиенту и полный HTML-документ, что обеспечивает более быструю [First Contentful Paint (FCP)](https://web.dev/articles/fcp), уменьшая [Total Blocking Time (TBD)](https://web.dev/articles/tbt), что также может снизить [Interaction to Next Paint (INP)](https://web.dev/articles/inp). Вот почему [команда Chrome рекомендовала](https://web.dev/articles/rendering-on-the-web) разработчикам рассмотреть возможность статического или серверного рендеринга вместо полного подхода на стороне клиента для достижения наилучшей производительности.

Использование сервера имеет свои компромиссы, и это не всегда лучший вариант для каждой страницы. Генерация страниц на сервере влечет за собой дополнительные затраты и требует времени на генерацию, что может увеличить [Time to First Byte (TTFB)](https://web.dev/articles/ttfb). Наиболее производительные приложения могут выбирать правильную стратегию рендеринга для каждой страницы, основываясь на компромиссах каждой стратегии.

Фреймворки предоставляют возможность использовать сервер на любой странице, если вы хотите, но не заставляют вас использовать сервер. Это позволяет вам выбирать правильную стратегию рендеринга для каждой страницы в вашем приложении.

#### Как насчет серверных компонентов {/*server-components*/}

Фреймворки, которые мы рекомендуем, также включают поддержку React Server Components.

Серверные компоненты помогают решить эти проблемы, перемещая маршрутизацию и получение данных на сервер и позволяя выполнять разделение кода для клиентских компонентов на основе данных, которые вы рендерите, а не только на основе отрендеренного маршрута, и уменьшая объем JavaScript, отправляемого для наилучшей [последовательности загрузки](https://www.patterns.dev/vanilla/loading-sequence).

Серверные компоненты не требуют сервера. Они могут быть запущены во время сборки на вашем CI-сервере для создания приложения с генерацией статического сайта (SSG), во время выполнения на веб-сервере для приложения с рендерингом на стороне сервера (SSR).

См. [Представляем React Server Components с нулевым размером пакета](/blog/2020/12/21/data-fetching-with-react-server-components) и [документацию](/reference/rsc/server-components) для получения дополнительной информации.

</DeepDive>

<Note>

#### Рендеринг на сервере — это не только для SEO {/*server-rendering-is-not-just-for-seo*/}

Распространенное заблуждение заключается в том, что рендеринг на сервере предназначен только для [SEO](https://developer.mozilla.org/ru/docs/Glossary/SEO).

Хотя рендеринг на сервере может улучшить SEO, он также улучшает производительность, уменьшая объем JavaScript, который пользователю необходимо загрузить и обработать, прежде чем он сможет увидеть контент на экране.

Вот почему команда Chrome [рекомендовала](https://web.dev/articles/rendering-on-the-web) разработчикам рассмотреть возможность статического или серверного рендеринга вместо полного подхода на стороне клиента для достижения наилучшей производительности.

</Note>
